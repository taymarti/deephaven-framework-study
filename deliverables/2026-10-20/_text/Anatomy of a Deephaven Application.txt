Anatomy of a Deephaven Application
Oct 20, 2026  ·  @Taylor
A Deephaven application is one worker's scripts, the update graph they build, the threads
and clients that feed and read it, and whatever it writes out; this doc maps all of it in space
and in time.
What we were missing
The biggest gap was control over time: a worker can run additional update graphs,
including an event-driven one that advances only when told, which is exactly a
framework-owned checkpoint. Everything else below fills in hooks, inputs, outputs and
operations we had not used.

Space: the application inside one worker
Everything the app does happens inside one worker process, around its update graphs
(one periodic graph by default, plus any event-driven graphs you add); clients, other
workers and your own subprocesses all reach it through one port.
Blue is the engine's graph; dashed orange is code you run outside the engine's control: a
thread inside the worker needs an execution context, while a subprocess can only be a
client.

Time: one application's lifecycle
Startup runs once, on whichever thread starts the server (the main thread in a stock
worker), and builds the graph; from then on the update graph's ticks drive everything, and
shutdown is only as orderly as your own cleanup.
Read a column top to bottom for one moment in time. Work from your thread waits for the
next tick, flows through the graph, and reaches clients as one consistent delta.
Who runs what: threads, processes and contexts
The engine owns most threads; your code runs on the thread that starts the server
(application-mode scripts, or an embedding host's server thread), on the script session,
inside listeners on update threads, or on threads and processes you start, and only those
last ones do not get an execution context for free. Thread names below are from our
introspection report on Community 42.6. Verified.

Persistence, serialization and shutdown
Nothing in a worker's memory survives it; an application persists only what it writes out,
and rebuilds from that in its next startup script.

The server's own files: notebooks and layouts saved by the web UI (the storage

Enterprise: database tables written through loggers and the Data Import Server or the

The definition, not the instance: a PQ's script, schedule and settings live in the
controller's store, not in the worker. Docs.
What crosses the wire
Tables travel as Arrow record batches: Flight for snapshots, Barrage for live change
sets.
deephaven.ui documents and callbacks travel as JSON-RPC over an object message
stream; tables inside them travel as tickets.
Custom plugins send whatever bytes they define, plus references to server objects.
Python state is yours. There is no deserialize hook; pickle or write it somewhere
durable and reload it at startup.
Shutdown
A worker stops when its process stops: Docker stop, the pip server's process exiting,
or an Enterprise scheduled stop.
Java-side cleanup is ordered by the JVM's shutdown manager; we found no
documented Python shutdown hook. With the pip server your launcher is __main__ ,
so its own finally  blocks and atexit  handlers are the natural place for cleanup on a
normal exit. Unverified; a hard kill skips all of it.
Clean up deliberately, in this order: set stop events for your threads and tasks, stop
listener handles (or close a liveness scope), flush sinks, release client tickets and close
sessions. Our tests showed that a leaked listener or task survives until the worker
restarts.
Deephaven as a service in our framework
Inverting the relationship avoids the lifecycle and shared-interpreter problems of running
a framework inside a worker: our process owns the event loop, its own checkpoint
schedule and the lifecycle, and starts Deephaven beside it as a service it reaches only as a

client. The data it reads still advances on Deephaven's ~1 s cycle, so this pattern does not

What each side does best:
Our framework keeps its asyncio loop, its own checkpoint rules, side servers,
subprocess pools and serialization.
Deephaven runs shared table logic on live data, serves dashboards, sinks to Parquet or
Kafka, and is reachable by other workers and browsers.

The boundary is one port. A Deephaven failure cannot take down the framework, and
the framework's memory and threads stay out of the worker.
We ran this pattern end to end ( tests/host_service_demo.py , native Windows). The
host started a second server as a subprocess, which was ready in 10.9 s. It deployed a live
aggregate with run_script  and read it at three checkpoints on its own 1.5 s clock. Per-
symbol counts went 6, 21, 26: they arrive in whole engine cycles, so they step unevenly
against our clock. A process pool ran unrelated computation alongside, and shutdown
closed the session and stopped the server. Verified.
One caveat surfaced: on Windows terminate()  is a hard kill (exit code 1), so the server
gets no chance to clean up. For a graceful stop, have the server shut itself down on
request, for example a run_script  that tells the launcher to exit, and flush sinks first.
The host side, condensed from the test:
class DeephavenService:
    """Start the server as a subprocess, connect as a client, stop it at 
shutdown."""
    def start(self, timeout=180):
        cmd = [self.server_python, "server/run_server.py", "--port", 
str(self.port), "--no-app"]
        self.proc = subprocess.Popen(cmd)          # JAVA_HOME must point at 
Java 17+
        deadline = time.time() + timeout
        while True:                                # port opens after startup 
finishes
            try:
                self.session = Session(host="localhost", port=self.port, 
auth_type="Anonymous")
                return self
            except Exception:
                if self.proc.poll() is not None or time.time() > deadline:
                    raise RuntimeError("Deephaven did not come up")
                time.sleep(2)
    def stop(self):
        self.session.close()                       # releases this client's 
tickets
        self.proc.terminate()                      # hard kill on Windows
        self.proc.wait(timeout=30)

Thread or subprocess: hosting Deephaven inside our process
Deephaven does not insist on the main thread: the pip server started and served clients
from a background thread of our own process, so the subprocess can become a thread, at
the cost of sharing one interpreter, one failure domain and our own globals.

The costs are in amber: one shared interpreter, and our module globals open to any client
