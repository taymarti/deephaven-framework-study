A Deephaven app is everything a worker built and kept alive: its interface is its named
fields, and its internals are the update graph, listeners and threads behind them. Clients
reach fields through tickets, and ticking data travels over Barrage.
At a glance
Named objects reach clients only through the field registry; everything a client derives
lives as an unnamed export in its session, and both end up as nodes in the same update
graph.

The model, tested
A worker has one Python namespace, and everything named in it is published: console
commands, run_script  calls and application-mode scripts all share it, and each
application adds its own fields on top.
In one paragraph: a worker is one JVM with one embedded Python interpreter and one
default update graph (more can be created, including an event-driven one). Its script
session owns a single global scope, and every exportable object bound to a name there is
a field of the scope  application. Application-mode apps can publish further fields under
their own ids. Together these form the field registry clients see. Each client session holds
export tickets for objects it fetched or created; these can branch from any node, add new
roots, or be promoted into the scope by binding them. Every table, named or not, is a node
in an update graph: the default one, unless it was built under an execution context bound
to another.
We checked each claim on Deephaven Community 42.6, running natively on Windows,
mostly with a two-app probe worker ( tests/probe_concepts.py ).

Tickets
A ticket is an opaque handle naming a server-side object; every client request takes
tickets in and hands new tickets back. The term comes from Apache Arrow Flight, the
transport Deephaven's client API is built on, where you fetch a stream by presenting its
ticket.
A typical request reads: take the object named by ticket X, apply this operation, put the
result under new ticket Y, now stream me Y.
The shaded bar is the export's lifetime: it ticks in the worker's update graph for as long as
the session holds its export ticket (export #7 here; the ticket itself is the byte e plus a 4-
byte number).

Formats are verified in the pydeephaven  42.6 source. The export lifetime comes from its
docstrings and the shared-ticket lifetime from a test; scope and application ticket
lifetimes are our understanding, not tested. A shared ticket's lifetime is the surprise: when
its publisher closed, fetching the ticket failed, and so did a copy that another session had
fetched while it was valid. To hand a table to other sessions durably, bind it to a name
instead ( bind_table ), which makes it an ordinary field.
A typed ticket is a ticket plus its object type (Table, Figure, deephaven.ui.Element , ...);
listing a server's fields returns typed tickets.
Exports explain the unnamed nodes an introspector finds. When a grid sorts a column,
the client asks for sort(trades)  under a new export ticket. That is a real, ticking node in
the worker's update graph, owned by the session and named nowhere; closing the
browser tab releases it.
What clients can and cannot do to a worker's graph:
Branch from any node they hold a ticket to, not only leaves: fields and their own
exports, mid-graph or not.
Never change existing computation. The graph only grows downstream; a parent
computes exactly as before. The shared costs are more work per cycle, more memory,
and a slow branch delaying the cycle for every table in the worker.

Barrage: streaming ticking tables
Barrage extends Arrow Flight so a client receives a snapshot followed by incremental
updates in the same shape the engine uses internally. Plain Flight can only send a table as
a one-off batch.
Each update cycle a table emits a change set: rows added, removed, modified and shifted.
Barrage serializes exactly that change set, plus Arrow record batches holding the new
values. The consumer applies it to its own copy, which therefore ticks too.
The consumer never recomputes the producer's logic; it replays the producer's change
sets onto its own copy.
Viewports. A client subscribes to a row range and a set of columns, such as rows 0–49
of Sym and Px. The server sends only what is visible and changed, which is how a grid
shows a million-row ticking table cheaply.
Consistency. Each message reflects one coherent update-graph step on the producer,
never half a cycle.
Coalescing. A slow or throttled subscriber receives several cycles merged into one
message, not a backlog.

Across workers on Enterprise
A table shared between PQs is a Barrage subscription, so it ticks on the consumer's clock,
one network hop and one cycle behind the producer.
A change waits for the producer's next cycle, crosses the network, then waits again for
the consumer's next cycle.
Each PQ has its own global scope. That is the scope  in
pq://RiskEngine/scope/positions : the field positions  in the scope application of
PQ RiskEngine. Docs (URI format).
The consumer gets a source node. uri.resolve("pq://...")  and remote_table
return a Barrage-backed table, which is a source in the consumer's graph. Docs (data is
copied into the consumer), Unverified (class naming).

Two clocks, not one. Within one worker, a join between two tables is consistent at
every step. Across workers, each side is consistent with itself, and the consumer sees
the producer as of the last message it applied.
Latency adds up: producer cycle, plus network, plus the consumer's next cycle.
Database tables live in no scope. db.live_table(...)  opens one into a scope by
binding it to a name, at which point it becomes a field like any other. Unverified.
A Code Studio is a temporary worker with its own, separate scope.
Identity, fields and persistence
An application id only means something inside the worker you are connected to; the
durable identity on Enterprise is the PQ, and durable state lives only where the app writes
it.
No API keys on application id across workers. Every address names the server or PQ
first; the app id never stands alone. Verified for URIs
( dh+plain://host:port/app/<id>/field/<name> ).
The same app id on two workers means nothing shared. Each worker has its own
registry. Across workers, fields are read-only: a subscriber gets a Barrage replica, and
writes to a replica do not reach the original. The only ways to change another worker
are writing to its input tables or running code in it, both as a client of that specific
worker.
PQ redundancy can run several workers for one PQ; as we understand it, each
computes independently rather than co-owning fields. Unverified.

Fields are an address book, not a permission boundary. They are the published
handles clients build on, but anything a client may do beyond them is governed by
authentication, console access and, on Enterprise, PQ permissions and table access
rules.
Coordination between PQs is by convention. Nothing checks that RiskEngine  still
publishes positions  with the expected columns until a subscription fails.
Nothing in a worker persists. When it stops, its fields are gone, and so is any record of
what they were. What survives is the PQ definition in the controller and whatever the
app wrote out: database intraday and historical tables, Kafka topics, files. A new
worker rebuilds from those in its startup script.
No stored interface contract. You cannot list a down PQ's fields; remote_table  even
fails against a stopped PQ unless the consumer supplies the table definition itself
(Docs). If the interface matters, keep a versioned list of field names and types in
source control and check it against the live worker, for example with the introspection
report.
What fields add beyond any app plus a database is sharing a live table by reference: every
client in a worker sees the same consistent step, and Barrage keeps other workers'
replicas current incrementally.

gap is dependency edges for nodes created before the ancestors log was opened.
