Purpose and scope
This note records what we learned building and probing Deephaven applications, and
recommends where application code should live on our Enterprise plant.
Tested hands-on: Deephaven Community Core 42.6, first in Docker and then as the
pip-installed server running natively on Windows, with deephaven.ui 0.42.2, plotly-
express 0.20.1, the @deephaven/*  web packages 1.30–1.31 and pydeephaven  42.6.
Not tested on our plant: Enterprise behaviour comes from Deephaven's public
Enterprise documentation. Confirm it against our installed version.

How the Deephaven runtime works
A worker runs your script once to declare a table graph; after that, the engine's update-
graph clock keeps the graph current, one cycle at a time.
Process lifecycle
This order is visible in the server log. Verified.
1. The JVM starts and loads configuration ( START_OPTS , deephaven.prop ).
2. Services are wired: authentication, sessions, object resolvers.
3. CPython is embedded through jpy, giving one global Python session.
4. Plugins register: table types, figures, deephaven.ui, JS plugins.
5. The update graph starts cycling.
6. Application scripts run, top to bottom, and must return.
7. The gRPC/HTTP port opens and clients can connect.
8. Steady state: update cycles plus client requests, until shutdown.
Three consequences follow:
The script is your only initialize hook. A ticking source starts ticking as soon as it is
created; there is no separate "start feeds" phase.

Nothing is restored on restart. The engine does not checkpoint a worker's in-memory
state; rebuild state from tables in the startup script.
Shutdown is Java-side. The JVM has an ordered shutdown manager, but we found no
supported Python shutdown hook. Treat shutdown as abrupt. Unverified.
The update-graph cycle
Each cycle refreshes every source, propagates the changes through the graph in
dependency order, then publishes the result. Verified.
Your code runs in the highlighted step: a listener's time is added to every cycle for every
table in the worker.
A cycle is a consistent checkpoint. Every table in the worker reflects the same step,
and a listener reading another table inside its callback sees that same step.
There is one default clock per worker. All sources and listeners on it share the
cadence, and rows that arrive mid-cycle wait for the next refresh. A worker can also
run extra update graphs, including an event-driven one that advances only when your
code calls requestRefresh() (Verified).
Updates are incremental. Operations receive row-level changes (added, removed,
modified, shifted) and update their results in place.
Listeners run inside propagation. A slow Python listener delays the cycle for every
table in the worker.

Threads
All Python on every thread shares one interpreter lock (the GIL).
Liveness and long-running work
References keep tables alive. A ticking table updates only while something references
it, and a name in the global scope is such a reference. In Community 42.6, top-level
names in application-mode scripts already live in the global scope, so they need no
global .
Do not loop in a script. A startup script that never returns blocks the worker's startup.
Sources do the waiting. Use time_table , the Kafka consumer or remote-table
subscriptions; for a custom feed, run your own thread and push rows into a
table_publisher .
Prefer query-language formulas. They compile to Java; Python called per row inside
update  takes the GIL on the update thread.

When to choose which
deephaven.ui suits internal and analyst tools written by Python teams. Costs: every
interaction is a server round trip, rendering uses server CPU per connected user, and
the page shell belongs to Deephaven.
React + @deephaven/*  suits the few apps that need their own routing, design system,
other data sources or a separate release cycle. Costs: a bootstrap chain to wire, table
and session lifecycles to manage, and packages that are built for Deephaven's own
monorepo first.

Deephaven as an application framework
Much of a hook-based event framework already exists in Deephaven, but the engine owns
time and the graph, so embedding such a framework in a worker means two runtimes in
one process.
The framework we compared against is a typical trading-style design. Users subclass an
Algorithm  and override hooks ( on_initialize , on_data , on_order_update ,
on_start_of_day , on_shutdown  and so on). An EventManager  owns an asyncio loop, the
feed tasks, a synchronizer that flushes feeds at checkpoints, a processing DAG, and side
servers: a websocket API, a diagnostics site and a REPL port.
The core difference: an event framework pushes events to user code and lets user code
change the plan at any time. Deephaven runs a graph that user code declared up front,
and user code is mostly gone after setup.

Where the runtime pushes back
The default checkpoint is global. The default clock is shared by everything in the
worker, with a latency floor of about one cycle plus listener time. An event-driven
graph lifts this: tables built on it advance only on requestRefresh(), and in our test one
refresh delivered three pushes as a single checkpoint (Verified).
Callbacks run on the update thread. A slow callback stalls every table on its update
graph (by default, every table in the worker), so real work has to be handed to another
thread, which reintroduces a second runtime; the server's executors (submit_task)
can run it on JVM threads instead (Verified).
Changing the graph from a callback is constrained. The usual pattern defers creation
to another thread under the update-graph lock ( deephaven.update_graph ).
Unverified detail.
Side servers do not fit. Inbound ports, TLS and routing are not provided for workers. A
REPL port inside a worker would also sit outside Deephaven's authentication,
permissions and audit.
Three realistic shapes
1. Deephaven-native rewrite. The framework becomes a thin library of conventions on
Deephaven primitives. Good when algorithms are table-shaped; an event-driven
update graph removes the fixed one-second checkpoint.
2. Standalone framework, Deephaven as a subprocess or remote service. Keep the
asyncio runtime, its checkpoint semantics and its servers, and reach Deephaven only
as a client. Verified end to end ( tests/host_service_demo.py ).

3. Embedded service on a thread. Start the pip server on a background thread of our

PQs; the framework runs standalone and subscribes to their results.

What this means for design:
The checkpoint you get is the engine's. It is consistent and free, but its cadence is set
per worker, not per algorithm.
Latency is bounded below by the cycle. The cycle length is configurable, but
shortening it applies to everything in the worker.
Incremental computation is real. Derived tables did their work without any per-tick
Python, and they were not the bottleneck.

Setup requirements
Open the ancestors log at worker start, before any tables are built. On Community we
did this from the first application-mode script.
Add Graphviz to the server image for SVG output. Text (DOT) output works without it.
The raw labels are Java descriptions. We wrote a small renderer
( examples/pretty_graph.py ) that adds Python variable names, plain-language
operations, per-interval cost and downstream arrows, and hides engine-internal nodes.
Blind spots
Only engine nodes appear. Asyncio tasks, Python state and queues are invisible; a
table_publisher  feed shows only as its output table.
Graphs are per node. They show what feeds one node, not a whole-worker map, and
there is no live view of a cycle in progress.
On Enterprise these logs are, we believe, persisted per worker as queryable tables, so
past PQs can be examined. Unverified.
Other tools worth trying: the server appears to support attaching a Python debugger (a
debugging initializer runs on the script thread), and standard JVM tools such as jstack
and Flight Recorder apply. Unverified.

The PQ model
One worker per PQ. Each PQ runs in its own worker JVM with its own heap and Python
interpreter; Core+ workers run the same engine as Community. Unverified (Docs list
worker and heap configuration).
A PQ is code plus settings. It holds Python or Groovy code and settings such as query
type, required heap and who can access it. Docs.
PQ types. Live Query (Script), Live Query (ReplayScript) and Batch Query
(RunAndDone) run on query servers. Merge, import and validation types run on merge
servers and need elevated privileges. Docs.
Interactive consoles are temporary workers of the same kind, without a schedule.
Docs (listed as an internal PQ type).
Sharing tables between PQs
Both methods copy data into the consuming worker and keep it ticking; the producer
needs no extra setup. Docs.

Running non-Deephaven applications inside a PQ
It works mechanically if the event loop runs on a background thread, but it is a worse
deployment target than a container. A top-level asyncio.run()  never returns, so the PQ
never finishes starting.
Shared interpreter. The app competes for the GIL with every Python formula, listener
and UI render in that worker.
Memory outside the heap limit. Python memory is not counted against the PQ's
configured heap, so a leak can exhaust the whole query server. Unverified in
Enterprise accounting.
Lifecycle mismatch. Scheduled stops are hard stops, failover can run two copies at
once, and asyncio signal handlers work only on the main thread.
No application health. A dead background thread leaves the PQ showing as running,
and nothing restarts it.
No ingress. No assigned ports, TLS or routing for inbound HTTP or websocket traffic.
Shared dependencies. Workers on a server typically share an admin-managed Python
environment. Unverified.
Identity. The app runs with the worker's account, credentials and data access, outside
the platform's audit of what it does.
Deephaven's marketing promises fast "analyses, models, algos, reports, and dashboards"
and tooling for "launching, scheduling, and monitoring applications". It does not claim that
arbitrary services run well as PQs, nor does it describe resource isolation between
workloads. Docs (Enterprise product page).

Weighing the arguments for "everything as a PQ"
Data locality is real for in-worker table operations. But PQ-to-PQ sharing is already a
network copy, and a client can create tables on the server and subscribe only to small
results. Placed in the same network, a client keeps most of the benefit.
Deployment and SDLC savings are real. But a PQ script is code. Deploying an
application as "configuration" puts it under a lighter change-control regime, which
tends to draw audit scrutiny once something important runs that way.
The savings move cost rather than removing it. All-in means one failure domain, one
shared Python environment, and every Deephaven upgrade becoming a regression
test for every app on it.
Testing is weaker. Unit tests, CI, code review and rollback are harder for PQ scripts
than for a normal repository and pipeline. Enterprise supports Git-sourced PQ scripts

Open questions for the vendor
These questions turn the Unverified items into written answers; ask the Deephaven
account or solutions team for responses on our installed version.
1. Resource isolation. If one PQ's Python leaks memory outside the JVM heap, what
protects other PQs on that query server? Are there per-worker memory or CPU limits?
2. Dependencies. Can one PQ have its own Python environment, or are environments
shared per server? What is the supported process for adding or upgrading a package?
3. Long-running non-table code. Is an asyncio service on a background thread inside a
worker a supported pattern? What happens to it on scheduled stop, failover and
restart?
4. Inbound traffic. Is a PQ hosting an HTTP or gRPC API supported? If so, how are ports,
TLS and routing handled?
5. Health. Can the controller detect that application code inside a running PQ has failed,
and restart it?
6. Graph changes at runtime. What are the exact rules for creating or closing ticking
tables from inside a listener?
7. Shutdown. Is there a supported Python hook that runs on scheduled stop?
8. Console attach. Can an authorized user open a console in a running PQ's scope?
9. Cycle tuning. Can the update-graph cycle length be set per PQ, and are additional or
event-driven update graphs supported inside PQ workers?
10. Upgrades. When Deephaven is upgraded, what regression burden should PQ owners
expect?
11. Reference customers. Do customers run general-purpose services, rather than
analytics, as PQs in production? What do those look like?
