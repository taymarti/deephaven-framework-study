Read this first
Deephaven is a live spreadsheet engine with a server attached, not an event-loop
framework. In QuantConnect LEAN you write callbacks ( Initialize , OnData ) that the
engine calls once per time slice. In Deephaven, your script runs once. It declares tables
and how each is computed from the others. From then on, the engine recomputes
everything that changed, about once a second by default, and pushes the changes to
every UI and client.
You write four kinds of thing. Everything else belongs to the engine:
1. Sources: where rows come from (a clock, Kafka, a Python feed you push into, a file, a
table another worker shares, a form a user fills in).
2. The graph: table operations that derive tables from tables (filters, formulas, joins,
aggregations, rolling windows). This is most of the program, and it is declarative.
3. Edges: the few places where Python code runs on changes (listeners), plus sinks that
write out.
4. Surfaces: what other people see and touch (named tables, deephaven.ui dashboards,
input tables, client APIs).
The rule of thumb that makes it click: if you would write it as a spreadsheet formula, it
belongs in the graph; if you would write it as a macro, it belongs in a listener, and you
should have very few. A trading app built this way has no OnData . Signals, positions and
risk are tables that are always current, and orders are rows that a listener sends out.
How to read this guide:
Anatomy shows what actually runs, on which thread, in what order.
Programming model is the construct catalog with exact syntax.
Extending and Backtesting answer what you can add and how history replays.
Worked engine shows one program end to end.
Deephaven vs. LEAN maps the concepts and states the limits.

Anatomy of a running app
A running app is one engine thread stepping the graph about once a second, while your
threads and the clients only queue work for the next step. Nothing you push is visible
until a refresh picks it up, and nothing a client sees is ever half a step.
Each lane is a kind of thread in one worker. The feed thread's rows and the client's
addRow()  wait in buffers until the refresh. The table operations, and then your listeners,
run inside the step while the lock is held. Only after the step completes do deltas go out
to grids and deephaven.ui. Console commands wait for the lock; submit_task  work runs
on its own JVM threads at any time.

Three gotchas we hit on native Windows:
1. Integer type hints fail. def f(qty: int)  and np.int64  are rejected with
"Unsupported type hint". Deephaven expects numpy code l  for 64-bit integers, but
on Windows numpy reports int64 as q . Use float hints with a (double)  cast, or run on
Linux.
2. query_library.import_static("com.acme.Risk")  fails with ClassNotFound for a jar
added through extra_classpath , although the JVM loads the class. Call by fully
qualified name, or import the Class object:
get_exec_ctx().j_exec_ctx.getQueryLibrary().importStatic(jpy.get_type("com
.acme.Risk").jclass) .
3. An unhinted Python function returns a PyObject  column, which formulas
downstream cannot do arithmetic on without a cast.

What Deephaven does not give you, compared with a backtesting platform:
No fill model, brokerage model, fees or slippage. Orders are rows; simulating fills is
your table logic.
No portfolio or securities objects. Positions and P&L are tables you build.
Time functions do not follow your clock in Community replay or event-driven
backtests. Use the data's own timestamps in formulas, not now() , and drive scheduled
logic from data, not time_table .
Look-ahead is still possible. Streaming replay is safe by construction, but a join against
a full historical table (reference data, end-of-day marks) can see the future. Point-in-
time joins ( aj ) avoid it.
External side effects in listeners (sending orders, HTTP calls) run during a backtest
too. Route them through one function you swap out.
A worked trading and risk engine
One function holds the whole strategy and risk engine as tables. We ran it live and as a
backtest on the same 900 quotes. Both ended with an identical book and desk risk, and
the backtest was 12 times faster. The full program is examples/06_trading_engine.py .

def build_engine(quotes, limits, desks):
    q   = quotes.update("Mid = (Bid + Ask) / 2")
    ind = q.update_by([ema_tick(5, "Fast = Mid"), ema_tick(20, "Slow = 
Mid")], by="Sym")
    sig = ind.update("Target = Fast > Slow ? 100L : -100L")                 # 
desired position
    orders = sig.update_by(delta("OrderQty = Target"), by="Sym") \
                .update("OrderQty = isNull(OrderQty) ? Target : OrderQty") \
                .where("OrderQty != 0") \
                .update(["FillPx = OrderQty > 0 ? Ask : Bid", "Notional = 
OrderQty * FillPx"])
    positions = orders.agg_by([agg.sum_(["Pos = OrderQty", "Cost = 
Notional"]), agg.count_("Trades")], by="Sym")
    book = positions.natural_join(q.last_by("Sym"), on="Sym", joins="Mid") \
                    .update(["Mtm = Pos * Mid", "PnL = Mtm - Cost", "Gross = 
abs(Mtm)"])
    risk = book.natural_join(desks, on="Sym", joins="Desk") \
               .agg_by([agg.sum_(["Gross", "PnL"]), agg.count_("Names")], 
by="Desk") \
               .natural_join(limits, on="Desk", joins="Limit") \
               .update("Breach = Gross > Limit")
    return {"signals": sig, "orders": orders, "book": book, "risk": risk}

Deephaven vs. QuantConnect LEAN
LEAN is a trading framework: it owns time, securities, orders and fills, and you fill in
callbacks. Deephaven is a data engine: it owns tables, recomputation and distribution,
and you supply the trading model. That is why the LEAN docs read as a recipe and these
read as a toolkit. Every LEAN concept has a Deephaven way to build it, but about half
have no built-in equivalent.

Where Deephaven is stronger:
Cross-sectional work over thousands of symbols at once, such as joins against
positions, reference data and limits.
Live risk roll-ups that stay current as any input changes.
Sharing: many teams and UIs see the same live tables.
Ad-hoc inspection of any table in a running app.
Where it is weaker for an algorithm framework:
No trading domain model: no orders, fills or portfolio, and no brokerage integration.
Python per-row and per-cycle callbacks are the costliest parts of the graph (about
195 ms per interval in our runs, against 3 to 36 ms for Java operations).
About 1 s default latency for externally pushed rows, unless you shorten the cycle or
step your own graph.
Time helpers follow the wall clock in Community replay.
Testing and lifecycle hygiene are yours: reloads, stuck listeners, shutdown.
The practical split for our firm: use Deephaven for the data and risk half (signals as tables,
positions, P&L, limits, dashboards, sharing). Keep the order, fill and broker half in our
algorithm framework, feeding Deephaven through table_publisher  and reading its
tables back. Or build that half once as a shared table library.

Rules and limits:
Frozen in backtest and test. Catalog and live-factory sources tick on the default clock,
so they are snapshotted in backtest and test modes. One graph cannot mix two clocks.
Backtest speed. run_history  replays history sources in time buckets, one
checkpoint per bucket: 900 quotes in 150 buckets took 1.3 s.
Laptop as a client of a real plant is not covered yet. On a laptop, remote names map to
local Community servers. Reaching a real plant from a laptop needs the Core+ client
and plant credentials.
Plant behaviour is unconfirmed. On Enterprise, state_table  and intraday_log
persist; on Community they live only in memory. Both paths go through dhfw , and the
Enterprise side is untested.
Testing on three tiers, and one API for both runtimes
Write against the Enterprise API. A thin wrapper, dhfw , forwards to Enterprise on the
plant and emulates the same calls with Community constructs on a laptop, so
application code never checks which runtime it is in. Tested: all 12 emulation checks pass
on Community 42.6 ( tests/test_dhfw_community.py ). The Enterprise forwarding is
untested here because we have no plant access; it calls the documented Core+ functions
directly.

What is not wrapped, because it is the same engine on both: table operations, listeners,
update graphs and execution contexts, table_publisher , deephaven.ui and plotly-

Core version, and dhfw.runtime()  warns when DHFW_PLANT_CORE_VERSION  differs from
the local one. Some things cannot be emulated at all: PQ scheduling, restarts and failover,
query servers, merge and validation jobs, and Enterprise authentication.
