Deephaven as an application framework: verified facts
ledger
One source of truth for every claim in our docs, deck and code. Each entry says how we know it. Verified =
observed by a test in this repo on Deephaven Community 42.6 (pip deephaven-server , native Windows, Java
17; earlier rungs also on the Docker image) or read in the installed 42.6 source. Docs = stated in Deephaven
documentation, not tested here.
Scopes, applications and fields
# Fact Evidence
S1 run_script  (Python client) and runCode  (JS API) run in the
worker's single global scope; a name defined by one call is visible to
the next
Verified: tests/probe_concepts.py
S2 Application-mode scripts run in that same global scope (globals()
is __main__.__dict__  was True). An undeclared top-level table
became a scope  field. global  is not needed in Community 42.6
Python (the docs still advise it)
Verified: tests/probe_app.d/scoping.py
S3 With the pip server, the launching script's __main__  is the console
scope: its own functions appear there, and a client's run_script
could read and modify the host's module globals
Verified: tests/probe_introspection.py ,
tests/embedded_thread_demo.py
S4 Underscore-prefixed names are published as scope  fields like any
other; an underscore does not keep a table private
Verified: tests/probe_concepts.py
S5 A worker holds several applications: scope  plus one per *.app  file;
a built-in app with no exports does not appear in the field list
Verified: tests/probe_concepts.py
S6 Two applications can each publish a field with the same name; each
resolves to its own object
Verified: tests/probe_concepts.py
S7 Fields are any registered object type (tables, figures, deephaven.ui
elements, partitioned/hierarchical tables, plugin objects)
Verified: field types listed by ListFields ;
plugin registration in server logs
S8 ApplicationState  (get_app_state()["name"] = obj )
publishes a field under the app's own id
Verified: tests/probe_app.d/scoping.py

Runtime: clock, threads, contexts
# Fact Evidence
R1 The default update graph cycles every ~1 s (target_cycle_ms  1000);
rows arriving between cycles are batched into the next one
Verified: rungs 1 and 4 (examples/ ),
introspection report
R2 Rows pushed from Python waited up to ~1 s (650–1,000 ms) before a
cycle picked them up
Verified: rung 4
R3 merged_listen  delivers one callback per cycle across all watched
tables, with None  for tables that did not change; a table read inside
the callback is consistent with that step
Verified: rung 4
R4 An exception in a listener stops it permanently while feeds keep
flowing
Verified: rung 4
R5 Re-running setup code stacks listeners unless the old handle is
stopped; background tasks that read lifecycle state from globals leak
until the worker restarts
Verified: rungs 3 and 4
R6 Execution contexts are per thread. The thread that started the server
holds the systemic context; on another thread, get_exec_ctx()
returns a static-only context and creating a ticking table fails
(UpdateGraphConflictException ). Capture the context on the
server's thread (or inside run_script ) and pass it in
Verified:
tests/embedded_thread_demo.py
R7 Server executors serial  and concurrent  exist;
submit_task("concurrent", fn)  ran Python work on a JVM thread
Verified:
tests/probe_runtime_features.py
R8 A second, event-driven update graph can be built from Python. Tables
built under a context bound to it (withUpdateGraph ,
table_publisher(update_graph=...) ) do not move on their own:
three pushes stayed invisible for 1.5 s, then one requestRefresh()
delivered them as one checkpoint (A: 600  = 100+200+300)
Verified:
tests/probe_event_driven_clock.py
# Fact Evidence
R9 The embedded server can be started on a non-main thread; the host's
asyncio loop kept running during startup but at about half speed (89
ticks of a 50 ms sleep in 9.4 s)
Verified:
tests/embedded_thread_demo.py
R10 In-process (embedded) use works without a client: tables built from the
host, a listener bridged into asyncio via call_soon_threadsafe
Verified:
tests/embedded_thread_demo.py
R11 GIL contention is real: while the host burned CPU in pure Python,
median listener lag rose from 36.6 ms to 74.8 ms (max 41 → 87 ms)
Verified:
tests/embedded_thread_demo.py
R12 Only one server per process: a second Server(...).start()  fails
with "Cannot create more than one instance of the server"
Verified:
tests/embedded_thread_demo.py
R13 The host process exited promptly once its main coroutine returned,
with the server on a daemon thread
Verified:
tests/embedded_thread_demo.py
R14 Hosting the server as a subprocess works: up in 10.9 s, logic deployed
with run_script , read at our own checkpoints; on Windows
terminate()  is a hard kill (exit code 1)
Verified: tests/host_service_demo.py
R15 Multiple update graphs per worker, each bound to an execution
context
Docs (event-driven case Verified, R8)
