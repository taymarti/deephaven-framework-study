Oct 21, 2026  ·  @Taylor
At a glance
Two thin layers on Deephaven let one codebase run on a laptop and on the plant. dhapp
gives an app its structure (roles, modes, a location-aware catalog, recipes, storage,
dashboards). dhfw  hides the differences between Community and Enterprise. Both are
in dhapp/  and dhfw/  in the repository. The engine's own API stays fully available.
Read it top to bottom. Your app calls dhapp , dhapp  calls dhfw , and dhfw  either forwards
to Enterprise or emulates on Community. Table logic in stages calls plain Deephaven
directly, on the right, because that engine is the same on both runtimes.
For how the engine itself works (cycles, threads, Barrage, replay), see the Programmer's
Guide. This document is the reference for building on the two layers.

Quick start: a working app in five steps
Declare sources, write stages, add actions, surface tables, then start in a mode. This is
the market-making demo in examples/mm_app.py , cut down.

from dhapp.ui import dashboard

"desk_limits", "plant": "ny"},
                   "desk_map":    {"db": ["Ref", "DeskMap"], "live": False}})
app = App("mm", catalog)
# 1. Sources: where rows come from
app.source("quotes", schemas.QUOTES, history=load_quotes)   # pushed live; 
replayed in backtest
app.source("limits", catalog="desk_limits")                 # resolved by 
location
app.source("desks",  catalog="desk_map")
# 2. Stages: pure functions; parameter names are table names
@app.stage
def orders(quotes):
    return 
recipes.fill_at_touch(recipes.target_to_orders(recipes.ema_cross(quotes)))
@app.stage

    return recipes.mark_to_market(recipes.positions(orders), quotes)
@app.stage

@app.action(on="orders", services=["broker"])

    broker.send(rows)

# 4. Surfaces: published fields, and the dashboard's panels
app.surface("book", "risk", "orders", "limits")

Stages run in dependency order, worked out from their parameter names. A name no

Three modes
Sources are frozen in backtest and test because one update graph cannot mix two ticking
clocks. Everything the app owns runs on the backtest clock.
The catalog. App code uses logical names ( desk_limits ). The Catalog  turns each into a
table, based on where the app is running. Moving a table to another PQ, or deploying onto
the plant that owns it, changes catalog entries or environment variables, never code.
Health. app.health  is a live table with one row per action: Calls , Errors , LastError . It
is published as <app>_health  and shown on the dashboard's status panel.
Runtime. Everything that differs between Community and Enterprise ( db , remote tables,
logging, controller imports, ACLs, identity) goes through dhfw , which forwards on
Enterprise and emulates on Community. Table operations, listeners and deephaven.ui are
the same engine on both, so they are not wrapped.

Running on the plant: the PQ script imports the app module from the controller
repository through dhfw.meta_import , sets DHFW_PLANT  and DHFW_PQ , and calls
app.start("live") . Use an Enterprise replay query for history at a simulated speed.
Cookbook
Add a live feed from any client SDK. Declare a pushed source, then call feed  from the
SDK's callback thread:
app.source("quotes", schemas.QUOTES, history=lambda: 
db.historical_table("MarketUs", "QuoteStock"))
# in your Solace, websocket or FIX callback:
app.feed("quotes", new_table([...]))          # rows appear at the next cycle
Read a plant table. Add a db  entry to the catalog, then use it as a source:
catalog.entries["quotes_us"] = {"db": ["MarketUs", "QuoteStock"]}
app.source("quotes", catalog="quotes_us")
On a laptop, put parquet files under DHFW_DATA_ROOT/MarketUs/QuoteStock/Date=YYYY-
MM-DD/ .
Subscribe to another PQ's table. Add an entry with pq , table  and plant . To keep the
transfer small, pass subscribe_kwargs  with filters  and included_columns . On
Community, dhfw shapes the table on the remote server with pydeephaven, so only those
rows and columns travel (tested). On Enterprise they go to remote_table's subscribe;
whether filtering happens upstream there is not yet verified.
catalog.entries["desk_risk"] = {"pq": "RiskEngine", "table": "desk_risk", 
"plant": "ny"}
rates = catalog.resolve("desk_risk", {"filters": ["Desk == `Rates`"], 
"included_columns": ["Desk", "Gross"]})

Three lifetime rules, all tested:
A subscription made before the pydeephaven  session closes keeps ticking afterwards.
A new subscription to that ticket fails once the session is closed.
If the published pydeephaven  Table object is garbage-collected, the ticket stops
resolving even while the session is open.
deephaven.barrage  or pydeephaven-ticking ? Inside a Deephaven server (a local app),
use deephaven.barrage . The result is a table in your graph that you can join, aggregate
and put on a dashboard. Use pydeephaven-ticking  only in a plain Python process with
no Deephaven engine, such as an asyncio service. It delivers per-update callbacks (added,
removed and modified rows), and you keep the state yourself. Its pip wheels are Linux
x86_64 only; Windows needs a source build of the C++ client.

Write your own recipe. It is a function from tables to tables, built from table operations:
def vwap(trades, by="Sym"):
    return trades.update("Notional = Px * Qty") \
                 .agg_by([agg.sum_(["Notional", "Volume = Qty"])], by=by) \
                 .update("Vwap = Notional / Volume")

Limits, open items and evidence
Everything below the Enterprise boundary was tested on Community 42.6. Nothing has
run on a plant yet, so the first task on Enterprise is to run the two test suites there.
Limits:
Frozen sources. Backtest and test modes freeze catalog and live=  sources, so a
backtest does not replay limit changes or remote updates over time.
Backtest speed. run_history  pulls history into Python (pandas) to slice it. Fine for a
day of quotes per symbol set, but for very large histories use an Enterprise replay
query.
Community emulation. On Community, state_table  and intraday_log  live in
memory and vanish on restart. Remote subscriptions have no reconnect policy, and the
pydeephaven sessions that shape them stay open until dhfw.remote.close_all(). ACLs
are not enforced.
No laptop-to-plant client binding yet. Developing on a laptop against the real plant's
tables needs the Core+ client and credentials; today remote names map to local stand-
in servers.
Simulated fills only. Recipes give the trading skeleton and a cross-the-spread fill
model, not a full order-management system.
